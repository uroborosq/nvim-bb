# Design

## Context

Мотивация описана в proposal.md (раздел Why), требования — в `specs/pr-change-tracking/spec.md`.

Текущее состояние, на которое опирается решение:

- `open_diffview` (`lua/bb_pr/init.lua`) выполняет fetch, checkout и merge ветки PR. Затем `set_current_tab_diff_base` записывает в `tab_state().diff_base` значения `{ root, base, source }`, где `source` — `origin/<from>` (вершина ветки PR), а `base` — merge base с target-веткой. Комментарии загружаются параллельно и попадают во вкладку через `set_tab_comments`. Через эту же функцию проходит и перезагрузка `reload_tab_comments`.
- В JSON комментария (`PRCommentView`) есть `id`, `version`, `parent_id` и `author`. В `author` записано отображаемое имя, поэтому надёжно определить «мой комментарий» в Lua нельзя. Добавление ответа не меняет `version` родительского комментария: у большинства родителей с ответами `version = 0` (проверено на PR 2730, 2749, 2753).
- В JSON PR есть `fromRef.latestCommit`, `toRef.repository.{slug, project.key}`, `state` и `my_review_status`. Последнее поле вычисляет `enrichPullRequests` через `userCandidates(cfg)` и `isCurrentUser`. Признака «я автор PR» нет ни в Go, ни в Lua: Lua только показывает `author.user.displayName`.
- Поле `commentCount` в JSON PR сейчас всегда равно 0. `PullRequest.CommentCount` (`main.go:85`) читает ключ верхнего уровня, а Bitbucket 8.9.7 передаёт значение только в `properties.commentCount`, рядом с `properties.openTaskCount` и `properties.resolvedTaskCount`. Проверка на 10 PR от 2026-10-11: `commentCount` — все комментарии, кроме задач, включая ответы; задачи = `openTaskCount + resolvedTaskCount`; длина вывода `bb -json -pr-comments` равна сумме трёх значений.
- Bitbucket 8.9.7 отдаёт `lastReviewedCommit` в `reviewers[]` самого PR, отдельный запрос не нужен. Проверка на `bitbucket.example.com` от 2026-10-11:

  | Статус ревьюера | Состояние PR | С `lastReviewedCommit` / всего |
  | --- | --- | --- |
  | APPROVED или NEEDS_WORK | открытые | 7 / 9 |
  | UNAPPROVED | открытые | 1 / 158 |
  | APPROVED | влитые | 285 / 292 |
  | UNAPPROVED | влитые | 2 / 962 |

  У автора PR поле не заполняется.
- Состояние плагина уже хранится в JSON в `stdpath("state")` через `read_json_file` / `write_json_file` (реакции, черновики).
- Окно PR Info при открытии вкладки автоматически не открывается: его открывают `:BBPRInfo` и переход к overview-комментарию.

## Goals / Non-Goals

**Goals:**

- Определение «что нового» не требует дополнительных запросов к Bitbucket при открытии PR и при построении списка.
- Сравнение комментариев не зависит от часов (локальных и серверных).
- Увиденный коммит остаётся доступным для diff после force push.

**Non-Goals:**

- Синхронизация отметок просмотра между машинами и с веб-интерфейсом Bitbucket. Из Bitbucket только читается `lastReviewedCommit`.
- Отслеживание реакций, смены статусов ревьюеров и статуса сборки.
- Отслеживание своих PR и PR в состоянии MERGED или DECLINED.
- Навигация «к следующему новому комментарию». Её можно добавить отдельным изменением.
- Ручная отметка «просмотрено» и откат отметки.
- Подсветка строк, изменённых с прошлого просмотра, в основном diff вкладки PR. Изменения кода видны в панели файлов и в отдельном diff (D8).
- Сообщение об удалённых комментариях.
- Сводка и пометки в PR Info, открытом из списка без вкладки PR.
- Сортировка и фильтрация списка PR по наличию изменений.

## Decisions

### D1. Локальная запись просмотра; Bitbucket используется только для чтения

Запись хранится в `stdpath("state")/bb_pr_seen.json`. Дополнительная точка отсчёта для кода — `lastReviewedCommit` текущего пользователя (D4).

Рассмотренная альтернатива — записывать просмотр в Bitbucket через `PUT .../participants/{slug}` с `lastReviewedCommit`. От неё отказались по четырём причинам:

1. Запрос обязательно задаёт статус. По документации `lastReviewedCommit` обновляется только при APPROVED или NEEDS_WORK, а статистика выше это подтверждает. Записать просмотр, не меняя ревью, нельзя.
2. Для пользователя, который не является ревьюером, запрос неявно добавляет его в участники PR. Это видно всей команде.
3. Для автора PR запрос завершается ошибкой.
4. Для комментариев локальное хранилище нужно в любом случае.

Синхронизация через Bitbucket дала бы выигрыш только для кода и только после Approve или Needs Work. Этот случай покрывает чтение `lastReviewedCommit`.

### D2. Формат хранилища

```json
{
  "version": 1,
  "prs": {
    "PROJ/repo#101": {
      "seen_at": 1791700000000,
      "source": "<sha вершины ветки PR>",
      "root": "<путь к репозиторию ревью>",
      "comment_count": 14,
      "comments": { "123": 2, "124": 0 }
    }
  }
}
```

- Ключ строится как `<toRef.repository.project.key>/<toRef.repository.slug>#<id>`. Он однозначен для всех репозиториев из `config.repos`.
- `comments` хранит словарь «id → version». Новый комментарий — id отсутствует, изменённый — версия отличается. Время не сравнивается, поэтому расхождение часов не влияет на результат.
- `comment_count` — число комментариев вместе с задачами, увиденных во вкладке: длина payload комментариев. Это то же число, что `commentCount + openTaskCount + resolvedTaskCount` в JSON PR (D10).
- `root` — репозиторий, в котором создана git-ссылка (D3). По нему ссылка удаляется при вытеснении и удалении записи.
- `seen_at` хранит локальное время и используется только для отображения («просмотрено 2 д назад») и для вытеснения старых записей.
- merge base в записи не хранится: смена merge base вычисляется заново при каждом открытии (D4).
- Запись выполняется как read-modify-write: файл перечитывается, обновляется только ключ текущего PR, затем файл записывается. Так несколько экземпляров Neovim не затирают записи о разных PR друг друга. Для одного и того же PR побеждает последняя запись.
- Вытеснение: после записи, если PR больше `since_last_view.max_count` (по умолчанию 200), удаляются записи с минимальным `seen_at` и их git-ссылки.
- Удаление закрытых PR: запись и её git-ссылка удаляются, когда PR встречается со `state` MERGED или DECLINED — в списке PR, запрошенном с другим `state`, или при открытии вкладки такого PR. Записи PR, отсутствующих в списке OPEN, не удаляются: при `limit` список может быть неполным.

### D3. Закрепление увиденного коммита git-ссылкой

`git update-ref refs/bb_pr/seen/<project>/<repo>/<id> <source>` выполняется в репозитории ревью при каждой записи просмотра. Ссылка защищает коммит от `git gc` после force push. `git fetch` с явными refspec-ами в `open_diffview` её не трогает.

Альтернатива — хранить только sha и при необходимости выполнять `git fetch origin <sha>`. Её отвергли: Bitbucket не гарантирует выдачу недостижимого коммита по sha. `git fetch origin <sha>` остаётся только для точки отсчёта из Bitbucket, у которой ссылки ещё нет.

### D4. Снимок точки сравнения при открытии вкладки

Отслеживание выполняется, только если PR в состоянии OPEN и `pr.is_mine` не установлен (D7). Для своих PR `tab_state().since` не создаётся, запись не читается и не пишется. Для PR в состоянии MERGED или DECLINED запись удаляется (D2).

В `open_diffview` после `set_current_tab_diff_base`:

1. Читается предыдущая запись по ключу PR, и её копия сохраняется в `tab_state().since = { prev, baseline, baseline_origin }`.
2. Выбирается точка отсчёта для кода `baseline`:
   - есть запись и есть `my_last_reviewed_commit` (при `use_bitbucket_baseline = true`): если `prev.source` — предок `my_last_reviewed_commit` и они не совпадают (`git merge-base --is-ancestor`), берётся `my_last_reviewed_commit` (`baseline_origin = "bitbucket"`), иначе `prev.source` (`"local"`);
   - есть только запись: `prev.source`, `"local"`;
   - есть только `my_last_reviewed_commit`: он, `"bitbucket"`;
   - нет ничего: `baseline = nil`, `"none"`.

   Если коммит из Bitbucket отсутствует локально, проверка предка не выполняется и берётся `prev.source`.
3. Асинхронно вычисляются данные для сводки и панели:
   - `git merge-base --is-ancestor <baseline> <source>` — линейное продолжение или переписанная история;
   - `git rev-list --count <baseline>..<source>` — число новых коммитов;
   - `git diff --name-only <baseline> <source>` — изменённые файлы, пересечённые со списком файлов PR из `with_pr_changed_files`;
   - признак смены merge base: `base_changed = not is_ancestor or merge-base(<baseline>, origin/<target>) ~= merge-base(<source>, origin/<target>)`. Если автор влил target-ветку или сделал rebase, merge base вершины сдвигается, а у старой точки остаётся прежним. Правило одинаково для обоих источников `baseline`.

   Результат сохраняется в `tab_state().since.delta`. Затем сбрасывается `state.panel_rendered_by_buf`, перерисовываются панель и PR Info, и выводится уведомление (D12).
4. Записывается новая запись: `source`, `seen_at`. Поля `comments` и `comment_count` переносятся из предыдущей записи и обновляются в `set_tab_comments` (D5).

Снимок делается один раз на вкладку. Последующие записи не трогают `tab_state().since`, как требует спецификация.

### D5. Комментарии: `set_tab_comments` как единая точка

`set_tab_comments` уже вызывается и при открытии PR, и при перезагрузке комментариев. Если у вкладки есть `since`, функция:

- объединяет версии всех комментариев из payload с `comments` записи, записывает `comment_count = #payload` и сохраняет запись;
- вычисляет `since.comment_marks = { [id] = "new" | "edited" }` относительно `since.prev.comments`. Комментарии с `is_mine` пропускаются. Если `since.prev` нет, вычисление не выполняется: точка отсчёта из Bitbucket к комментариям не применяется.

Любое изменение `version` даёт пометку «изменён», в том числе resolve, смена состояния задачи и превращение комментария в задачу.

Пометки читаются при рендеринге из `since.comment_marks` по `id`. Затронутые места:

- `format_comment_header`: PR Info и всплывающее окно — общий код для overview- и file-комментариев;
- `render_buffer_comments`: виртуальный текст.

Memo `rendered_by_buf` уже инвалидируется сменой payload. Снимок `since` для вкладки неизменен, поэтому новых ключей в memo не требуется.

### D6. Определение собственных комментариев в Go

В `PRCommentView` добавляется `is_mine bool` (`json:"is_mine,omitempty"`). Значение вычисляется через существующие `userCandidates(cfg)` + `isCurrentUser(cmt.Author)` при сборке вида комментария.

Альтернатива — сравнивать `author` с именем пользователя в Lua. Её отвергли: `author` содержит отображаемое имя, а Lua не знает `config.user`.

### D7. Новые поля JSON PR

- В `Reviewer` добавляется `LastReviewedCommit string` (`json:"lastReviewedCommit,omitempty"`). В `PullRequest` добавляется `MyLastReviewedCommit string` (`json:"my_last_reviewed_commit,omitempty"`). Оно заполняется в `enrichPullRequests` рядом с `MyReviewStatus`, тем же поиском текущего пользователя среди ревьюеров.
- В `PullRequest` добавляется `IsMine bool` (`json:"is_mine,omitempty"`): `isCurrentUser(pr.Author.User, candidates)`, заполняется там же.

### D8. Diff «с последнего просмотра» (`<leader>rn`)

- Глобальная клавиша `since_last_view.diff_map` (по умолчанию `<leader>rn`) и команда `:BBPRSinceLastView` регистрируются через `bind_keymaps(nil, ...)`, как `pr.merge_map`. Вне вкладки PR выводится предупреждение. В своём PR выводится уведомление «для своих PR отслеживание отключено».
- Команда: `DiffviewOpen -C<root> <baseline>..<source>`. Если `since.delta.base_changed`, к команде добавляются `-- <файлы PR>`, а пользователь получает уведомление об ограничении.
- Если `<baseline>` отсутствует локально, сначала выполняется `git cat-file -e`, затем один `git fetch origin <sha>`. При неудаче выводится уведомление, и Diffview не открывается.
- Diffview открывается в новой вкладке без `tab_state().pr`. `close_old_pr_tabs` закрывает только вкладки с `pr`, поэтому эту вкладку пользователь закрывает сам (`:DiffviewClose`). Комментарии в ней не рисуются: её `tab_state` не содержит `comments`.

### D9. Пометки в панели Diffview

> Заменено изменением `track-viewed-files`: в панели показывается состояние просмотра файлов, знак `◆` удаляется.

`apply_comment_indicators_to_diffview_panel` расширяется. Помимо текущего множества «есть комментарии» используются ещё два множества:

- `since.delta.changed_files` — файлы, изменённые в коде;
- файлы с новыми или изменёнными file-комментариями.

Для этих пометок используется отдельный знак и highlight `BbPrSinceLastView`, связанный по умолчанию с `DiagnosticInfo`. Memo панели дополнительно учитывает `since.delta` и `since.comment_marks`.

### D10. Маркер в списке PR

`format_pr_entry` и `build_lines` получают одну колонку шириной 4 символа перед текущим содержимым. Колонка строится по записи из хранилища, которое загружается один раз на вызов списка. Порядок строк не меняется.

Колонка пустая для своих PR (`is_mine`) и для PR в состоянии, отличном от OPEN. Для остальных PR:

| Ситуация | Вывод |
| --- | --- |
| нет записи и нет `my_last_reviewed_commit` | `·` |
| нет записи, `latestCommit ~= my_last_reviewed_commit` | `◆` |
| есть запись, `latestCommit ~= record.source` | `◆` |
| есть запись, `total > record.comment_count` | `+N`, где `N = total - record.comment_count` |
| изменений нет | пробелы |

Здесь `total = commentCount + openTaskCount + resolvedTaskCount`. `◆` и `+N` могут выводиться одновременно, например `◆+3`. Для PR без записи `+N` не выводится: базы для комментариев нет.

При построении списка, запрошенного с `state`, отличным от OPEN, записи PR в состоянии MERGED или DECLINED удаляются (D2).

### D11. Конфигурация

```lua
since_last_view = {
	enabled = true,
	store_path = vim.fn.stdpath("state") .. "/bb_pr_seen.json",
	max_count = 200,
	diff_map = "<leader>rn",
	use_bitbucket_baseline = true,
	notify = true,
},
```

При `enabled = false` хранилище не читается и не пишется, `tab_state().since` не создаётся, клавиша не регистрируется. Все места рендеринга проверяют только наличие `since`.

### D12. Уведомление после открытия

> Отменено изменением `track-viewed-files`: PR Info открывается автоматически при каждом открытии PR, уведомление и параметр `notify` удаляются.

Когда готовы и `since.delta`, и `since.comment_marks` (или стало известно, что комментарии не размечаются), выводится одно `vim.notify` уровня INFO, если `since_last_view.notify = true` и есть что-то новое:

- `bb_pr: с последнего просмотра (2 д назад): 3 новых коммита, 2 новых и 1 изменённый комментарий`;
- при переписанной истории вместо числа коммитов — `история ветки переписана`;
- при `baseline_origin = "bitbucket"` к части про код добавляется `(от вашего ревью в Bitbucket)`; время берётся из `prev.seen_at` только при наличии записи.

При первом открытии (`baseline_origin = "none"`) и когда нового нет, уведомление не выводится. Ошибка загрузки комментариев не задерживает уведомление: оно выводится с частью про код.

### D13. Чтение счётчиков комментариев из `properties`

В `PullRequest` добавляются `OpenTaskCount int` (`json:"openTaskCount"`) и `ResolvedTaskCount int` (`json:"resolvedTaskCount"`). `PullRequest.UnmarshalJSON` декодирует структуру через тип-псевдоним, затем копирует `properties.commentCount`, `properties.openTaskCount` и `properties.resolvedTaskCount` в соответствующие поля. Так значения доступны во всех местах декодирования PR, а колонка CMTS табличного вывода перестаёт показывать 0.

Это исправление ошибки, оно не зависит от остальной фичи и выполняется отдельной задачей.

## Risks / Trade-offs

- [Слияние target-ветки в ветку PR] → Diff ограничивается файлами PR (D8). Если в файл PR одновременно пришли изменения из target-ветки, они попадут в diff. Это допустимо, пользователь получает уведомление.
- [`version` комментария меняется не только при правке текста, но и при resolve или смене состояния задачи] → Такой комментарий помечается как «изменён». Это выбор пользователя: смена состояния задачи для ревьюера — значимое событие. Ответ в ветке `version` родителя не меняет. Если пометок окажется слишком много, можно хранить дополнительно хеш текста и различать «изменён» и «статус изменён» без миграции.
- [Пометка просмотра ставится при открытии, даже если PR не дочитан] → Пометки остаются видимыми до закрытия вкладки. Это выбор пользователя (открытие = просмотр).
- [Два экземпляра Neovim открыли один PR] → Побеждает последняя запись. Потеря ограничена одним PR.
- [Счётчик в списке учитывает удаление комментариев] → Если удалили столько же комментариев, сколько добавили, маркер `+N` не появится. Это допустимо для эвристики без запросов, точная картина видна при открытии.
- [Собственный комментарий, оставленный в веб-интерфейсе после закрытия вкладки] → Даёт `+1` в списке: отличить его без запросов нельзя. При открытии PR этот комментарий не помечается (`is_mine`).
- [Рост числа ссылок `refs/bb_pr/seen/*`] → Их число ограничено `max_count`, а записи закрытых PR удаляются вместе со ссылками.
- [Записи PR, которые закрылись и больше не встречаются в списке] → Удаляются только вытеснением по `max_count`.

## Migration Plan

Миграция данных не требуется: хранилище и ссылки создаются при первом открытии PR. Новые поля Go CLI только добавляются, поэтому старый плагин с новым CLI работает. Новый плагин со старым CLI тоже работает с ограничениями:

- нет `is_mine` у комментариев — свои комментарии помечаются как новые;
- нет `is_mine` у PR — свои PR отслеживаются;
- нет `my_last_reviewed_commit` — точки отсчёта из Bitbucket нет;
- `commentCount` и счётчики задач равны 0 — маркер `+N` не выводится.

Откат: `enabled = false`. Для полной очистки удаляются `bb_pr_seen.json` и ссылки командой `git for-each-ref --format='%(refname)' refs/bb_pr/seen | xargs -n1 git update-ref -d`.

## Open Questions

- Выдаёт ли `bitbucket.example.com` коммит по `git fetch origin <sha>`, если коммит недостижим ни из одной ветки? Это влияет только на текст уведомления в запасном сценарии D8.
- Конкретные символы и highlight-группы пометок уточняются при реализации и не меняют поведения.
